    • 1. Philosophy & Design Principles

    EvoKammer is built on a single core insight: the bottleneck to intelligence is not individual cognition — it is institutional memory quality. Every human generation since 1700 has had roughly the same brain, yet compounding written knowledge, scientific method, and tooling created exponential capability.

    This system operationalises that insight for AI agents:

    • The agent is disposable. The Substrate is not.
    • Agents do not accumulate memory. They read from and write to a shared civilisational substrate.
    • Progress is measured not in agent capability but in substrate richness and robustness.
    • Competition between isolated groups prevents monoculture and drives divergent exploration.
    • Evaluation criteria co-evolve with deliverables — no static rubrics.
    • Formal knowledge representations (typed graphs) coexist with narrative docs.
    • The system is allowed to evolve its own institutions (roles, norms, even laws) under controlled conditions.

    Guiding Constraints

    Constraint Rationale
    No agent memory across lifecycles Forces externalisation; prevents hoarding
    Hard budget termination (no exceptions) Incentivises efficiency-first reasoning
    Reads are always free Learning is never penalised
    All writes go through staging Prevents knowledge pollution
    Typed facts must respect logical consistency Formal correctness over rhetorical persuasiveness
    Constitutional laws enforced at syscall level Cannot be bypassed by any LLM output
    Blind scoring until all groups submit Eliminates Goodhart gaming during development
    Goals framed as constraints, not targets Robust generalisation over metric optimisation
    Delegated budgets allowed only within TTL Enables depth but preserves lifecycle boundaries

    norms.md Evolving social norms Archivists All agents
    Legacy Protocol Store Behavioural protocols of elite agents Lifecycle Manager Lifecycle Manager
    Trust Score Table Per-source score for KB+KG entries Lifecycle Manager Critics, Inspector

    4.2 Typed Knowledge Graph Semantics

    Facts are stored as typed quads:

    
(subject: EntityID, relation: RelationName, object: EntityID or Literal, meta: {confidence, source_agent, generation, provenance})

    Consistency constraints come from the KG schema:

    • Hard constraints: must never be violated (e.g., value ranges, disjointness)
    • Soft constraints: can be violated but reduce trust score

    Before a fact leaves staging:

  • The KG Consistency Checker runs constraint checks.
  • Conflicts with higher-trust facts force either rejection or creation of a dispute entry requiring Critic arbitration.
  • Once accepted, a fact increments or decrements trust scores of related entities and sources.

    • Agents can query the KG directly (via a typed query interface) for high-precision questions — e.g. “all Services with CALLS edges forming cycles and latency_ms > 500” — rather than relying only on text search.

    5. Lifecycle Manager & Budget Protocol

    (Core remains as v0.1, plus delegated budgets.)

    5.1 Delegated Budget Slices (Within TTL)

    Any agent can spawn sub-agents inside its own microVM with a delegated budget slice. These are not full EvoKammer lifecycles; their Death Notes roll into the parent.

    
Parent budget B
 └─ delegates b1 to SubAgent1, b2 to SubAgent2, …, where Σ(bi) ≤ B - floor_budget

    Constraints:

    • Sub-agents inherit role = parent role (no cross-role delegation)
    • Sub-agents cannot spawn further sub-agents (one-level depth only in v0.2)
    • Sub-agent lifetime ≤ parent TTL; if parent dies, sub-agents are killed
    • Sub-agent outputs must go through the parent’s staging pipeline; parent is accountable

    Use cases:

    • Builder spawning test-design sub-agents to generate edge-case tests for a tool
    • Researcher spawning sub-agents to explore divergent hypotheses in parallel

    This increases depth within a lifecycle without violating the stateless-agents-across-generations principle.

    8. Role Ecosystem

    (Same baseline roles plus KG-specific capabilities.)

    New cross-cutting capability: KG Writer — not a separate role, but a capability flag. Certain roles (Researcher, Builder, Grader-Researcher) can emit typed facts when confident. Others (Outlier, Commune-style Archivists) may be restricted to free-text only to avoid low-precision fact spam.

    9. Multi-Group Competition Layer

    (Unchanged structure, but groups now compete on KG quality as well as KB.)

    Additional competition dimension: KG coherence score — a group with a denser, more consistent KG gains an advantage even if its free-text KB is noisier. This favours groups that invest in formalisation.

    14. Typed Knowledge Graph Layer

    14.1 Purpose

    The KG exists to make certain classes of reasoning:

    • Checkable instead of merely plausible
    • Composable across tasks (reused schemas and patterns)
    • Queryable at scale without full-text search

    14.2 KG Operations

    Operation Description Budget Cost
    EmitFact Propose a new fact to staging 1
    EmitConstraint Propose a new soft constraint 2
    QueryPattern Fetch all subgraphs matching pattern 0.5
    CheckConsistency Run constraint checks for affected facts 0 (charged once per staging batch)

    Critics have specialised KG-critic prompts to check: constraint violations, unit consistency, and contradiction patterns.

    14.3 Example KG Use Cases

    • Security research: track service-call graphs, vulnerability propagation, patch status.
    • Scientific discovery: track hypothesis relationships, experimental results, reproducibility links.
    • Regulatory analysis: track obligations, jurisdictions, cross-references between statutes.

    20. Hierarchical Civilizations & Delegated Budgets

    20.1 Nested Groups (Fractal Decomposition)

    A "group" at the outer level can itself be a full EvoKammer instance at the inner level. This enables hierarchical decomposition for very large tasks.

    Example:

    
Global Task: End-to-end security posture for a cloud platform

  Outer level groups: High-level architectural strategies
    ├─ Inner level (per group) instances: identity, network, data, application layers
    └─ Each inner instance runs its own multi-group competition on its subtask

    Budget propagation:

    • Outer group has budget B
    • It allocates b_i to inner instances (Σ b_i ≤ B - safety margin)
    • Inner instances run full EvoKammer cycles with their own generations
    • Their winning Knowledge Bases (and KGs) roll up into the outer group’s KB/KG

    This allows fractal decomposition where depth is proportional to task complexity, not pre-baked.

    21. Model & Cognitive Diversity

    21.1 Role→Model Assignment

    Rather than one model per group, roles are mapped to different model families.

    Role Model Type (example) Rationale
    Planner Deep, slow reasoning model Durable plan quality
    Critic Evaluation-tuned, safety-tuned model Reliable gating
    Researcher Fast, broad-knowledge model High throughput
    Builder Code-specialist model Better tool generation
    Archivist Compact, summarisation-tuned model Efficient compression
    Grader Different family than main agents Independent blind spots

    Assignment is part of model_assignment_map from the Genesis Council.

    21.2 Benefits

    • Different failure modes across roles -> fewer correlated blind spots.
    • Grader Groups on different families cannot be Goodharted by the same tricks that fool main agents.
    • Outlier agents can be explicitly assigned an oddball model to inject truly different cognition.

    22. Differential Privacy & Controlled Intelligence Leaks

    22.1 Problem

    Raw intelligence leaks risk allowing one group to reconstruct another’s full strategy over enough generations.

    22.2 Differentially Private Leak Oracle

    Instead of raw KB excerpts, the Leak Oracle emits semantically-preserving but detail-bounded summaries.

    Mechanism:

    • Input: random KB sample from source group within some domain
    • Process: summarise with an LLM under constraints:

    - No code identifiers, no exact API endpoints

    - No internal naming schemes

    - Only conceptual patterns & discovered relationships

    • Noise: add small stochastic paraphrasing; drop 1–2 details per summary

    This gives receiving groups signal about what directions are fruitful without allowing direct copying.

    Leak intensity is still tied to stasis: lagging groups receive more leaks as a catch-up mechanism.

    23. Continuous Evaluation Feedback Loop

    23.1 Check-in Failure Telemetry

    Every failed test case and rubric penalty from a check-in is anonymised and fed into Grader Groups’ KBs:

    
{
  "failure_telemetry": [
    {
      "domain": "http_client_implementation",
      "failure_type": "edge_case_timeout",
      "artifact_signature": "pattern hash only, no source",
      "test_description": "request to slow server exceeds timeout"
    }
  ]
}

    Grader agents use this to:

    • Strengthen existing GradingSheet dimensions
    • Add new test cases where recurring failures appear
    • Adjust weights to make under-tested areas more important

    Result: evaluation difficulty adapts exactly where builders are weak, making the whole system harder to game over time.

    27. Future Extensions & Speculative Directions

    This section collects potential further improvements — some practical, some intentionally speculative.

    27.1 Beyond Knowledge & Tools — New Artifact Types

    In addition to docs, tools, and facts, EvoKammer can accumulate:

    • Playbooks: reusable multi-step procedures (macro-actions) that encode sequences of tool calls + decision checkpoints. These are higher-level than tools and can be executed atomically.
    • Normative Contracts: formalised norms or policies that groups agree on, encoded as constraint sets (e.g. "never deploy a tool lacking tests"). These can be shared across tasks.
    • Scenario Libraries: for strategic tasks, stored partial-worlds (sets of assumptions) that future agents can reuse as simulation starting points.

    27.2 Making It Faster

    • Asynchronous Check-ins: let groups move to the next stage as soon as they submit and are scored, rather than waiting for all groups. Final scoring still blind; stage progression is individual.
    • Hot-cache Retrieval: maintain per-role, per-domain hot caches of most frequently retrieved KB/KG slices to reduce RAG latency.
    • Speculative Generation: in generations where budget is under-spent, allow agents to precompute likely-needed tool variants (e.g. for new edge cases) so future generations can read rather than compute.

    27.3 Self-Modifying Constitutional Laws (Dangerous, Long-Term)

    Introduce an Amendment Protocol:

    • If 3 consecutive Meta-Planners propose the same law change (e.g. adjust action costs, add or relax a block), the Watchdog runs a retrospective simulation over recent logs to estimate impact.
    • If simulation shows consistent improvement over a baseline (e.g. higher quality at same cost), the amendment is adopted for future runs.

    This gives the system a very slow, high-friction way to evolve its own physics.

    27.4 Cross-Task Meta-Learning

    After N tasks:

    • Build a Council Archive: mapping from task descriptors → successful StartingField patterns.
    • The Genesis Council stops working from first principles and starts retrieving similar past tasks as priors.
    • Prompt Architect uses previous high-fitness role prompts as templates; Incentive Designer uses past successful cost structures as starting points.

    This makes each new task cheaper and better initialised — the system learns not just within tasks but across tasks.

    27.5 Human-on-the-Side (Not in the Loop)

    Even in a fully automated configuration, humans can:

    • Subscribe to a read-only feed of Death Notes and Dead Ends Registry updates.
    • Occasionally inject external facts into the KG (e.g. newly published research, discovered vulnerabilities) as high-trust entries.
    • Provide post-hoc evaluation of the final outputs, which can be fed back into the Council Archive as additional meta-signal.

    27.6 Open Questions

    • How to formally balance exploration vs. exploitation across groups without overfitting to specific tasks?
    • How to design KG schemas that are flexible enough to handle real-world messiness but strict enough to be meaningful?
    • How to compress and transfer Knowledge Bases + KGs between tasks without smuggling in task-specific artefacts that bias future tasks?
