    EvoMolior Competitive Progressive-Disclosure Architecture#

    Executable architecture overview and combined action plan#

    Status: proposed refinement of the current EvoMolior architecture, not a replacement architecture
    Evidence cut: 11 July 2026
    Required invariant: every normal run remains input → Genesis Council → competitive worker/delivery groups + parallel competitive grader groups → sealed end-round check-in/evaluation → resource and disclosure update → next round → final publication.

    Architecture decision. This plan explicitly rejects replacing EvoMolior with a single-agent-first router or a centralized expert-merger pipeline. The competitive, generational society remains the product. The improvements below make that society more coherent, more causally measurable, and better aligned with the intended design: short-lived agents must overcome bounded limitations, leave useful durable state, and disappear.

    Executive decision#

    EvoMolior should be refined around one central object: a sealed, versioned Progressive Limitation and Capture Node Atlas generated by the Genesis Council from the receiver's underlying need.

    The Atlas is not merely a task list. It is the authoritative representation of:

    • the receiver's ultimate reason for needing the deliverable;
    • the limitations that prevent that receiver outcome;
    • the dependency tree from atomic knowledge or experiment leaves to integrated deliverable roots;
    • the progressively disclosed information available at each stage;
    • the proof contract by which each node is graded at round end;
    • node ownership, recapture, yields, and competitive benefits;
    • tool and simulation opportunities;
    • the lineage from agent contributions to the final deliverable.

    Workers do not receive the entire original task. They receive a bounded stage view and, usually, one atomic node. The full map topology may be visible as a committed skeleton, but unrevealed node payloads remain opaque. The run proceeds leaves-to-root, while the Council's reasoning proceeds receiver-why-to-leaves.

    The most important changes are:

    1. Unify the node systems. Derive WIP tasks, deliverable skeleton, resource map, disclosure state, and node grading from one NodeAtlas instead of maintaining several partially overlapping structures.
    2. Compile the Council output. Pass hard runtime constraints into the Council and reject or selectively regenerate infeasible fields; never silently rewrite material Council decisions.
    3. Make mortality productive. Every ordinary agent receives an explicit TTL and a ContributionCommit contract. Success means an accepted artifact, evidence-backed negative result, reusable tool, or structured dead end—not merely a fluent final message or synthetic fallback.
    4. Formalize Outlier novelty. Outliers receive no ordinary node assignment and no legacy. They must introduce a falsifiable new vector, layer, representation, risk, or approach. Accepted proposals become versioned shadow nodes or map amendments.
    5. Make grader civilizations truly competitive. Grader groups create and improve requirement graphs, hidden tests, adversarial cases, and scoring methodologies before seeing worker submissions. They compete on breadth, depth, robustness, creativity, calibration, executability, and parsimony.
    6. Grade every open node at round end. Worker groups submit node evidence packets; grader groups return exact-cardinality bundles; the MetaJudge may advance disclosure or allocate resources only after a valid quorum.
    7. Reward downstream utility. Node capture, agent fitness, tool fitness, and legacy selection depend on accepted node closure, later reuse, verifier passes, and final-deliverable lineage—not staging volume.
    8. Treat cheap single-family runs as an engineering mode, not evidence of cognitive diversity. The system can be made reliable with strong schemas, small node contexts, deterministic validation, and constrained tool templates. Robust grader independence, difficult synthesis, and creative tool construction may still require selective stronger or different-model calls.
    9. Give every mortal agent an immutable model phenotype, not only a role prompt. A phenotype may combine one shared base checkpoint with a learned adapter, soft prefix, decoding policy, optional steering or routing intervention, verifier, and lineage hash. It is fixed at birth, evaluated after death, and may influence only future agents at a sealed round barrier.

    1.1 What the maintained architecture already provides#

    The current production flow already matches the required high-level architecture: raw objective and artifacts feed the Genesis Council; a sealed StartingField feeds isolated group substrates and finite agents; worker outputs pass through staging and Critic authority; group coordination owns leaks, dispatches, disclosure, and capture; isolated grader groups feed blind scoring and MetaJudge; final synthesis passes a publication contract and archive. [S2:36–98]

    The deep dive also confirms that the existing StartingField already contains a node graph, deliverable skeleton seed, stage contents, model assignments, score normalization, primordial tools, sealed tests, and a consistency report. [S1:602–645] The current resource map can claim or recapture nodes and apply later budget yields. [S1:714–724] Progressive disclosure already tracks a per-group stage and advances or holds groups at check-ins. [S1:791–804]

    These are the right primitives. The plan below makes them one coherent execution system.

    1.2 What the historical run proved#

    The supplied run did prove operational compounding:

    • two worker groups progressed from 3/8 completed WIP nodes in round 0 to 8/8 by round 2;
    • group KBs grew from seven primordial entries to 22 and 20;
    • outputs passed through staging and Critic review;
    • agents died while durable state survived;
    • isolated worker and grader substrates, round summaries, and final publication all executed.

    That is meaningful evidence for the substrate thesis: the civilization can retain work beyond an individual agent's context and lifespan. [S4:41–73]

    1.4 The retained product thesis#

    The correct thesis is not merely “many agents are better.” It is:

    A population of context-limited, mortal agents can explore and validate a progressively revealed limitation landscape more effectively when durable knowledge, tools, failures, node ownership, and grading survive them.

    The architecture must make that claim measurable node by node and round by round.

    2. Non-negotiable system invariants#

    The following invariants define the product and must remain true through implementation.

    ID Invariant Consequence
    I-01 A normal run always begins with Council generation of sealed worker and grader fields. No single-agent-first routing path replaces Genesis.
    I-02 Two or more worker/delivery groups compete in semi-isolated substrates. Group identity, ownership, and resource trajectories remain meaningful.
    I-03 Two or more grader groups independently create criteria and judge blind submissions. Evaluation is a competitive civilization, not one static rubric prompt.
    I-04 Every ordinary agent has bounded context, action budget, and TTL. No agent becomes the durable mind of the run.
    I-05 Every ordinary agent must attempt a useful durable commit before death. A fluent final answer alone is not success.
    I-06 Workers normally see only the current stage and assigned limitation node, not the full final objective. Progress emerges through disclosure and substrate accumulation.
    I-07 Outliers receive no ordinary task instruction and no legacy protocol. Their function is independent novelty, not completing a disguised WIP node.
    I-08 Every revealed/open node is evaluated at the round boundary. Resource and disclosure decisions have explicit evidence.
    I-09 Missing grader data is invalid/abstained, never silently converted to zero. A malformed evaluation cannot change the civilization.
    I-10 Capture is decided by node-specific grade, not completion order. Competition rewards quality rather than racing.
    I-11 Council output is executable as sealed or fails compilation. Runtime does not silently erase designed diversity.
    I-12 Final publication occurs only after a quiescent archive barrier. The archive represents a complete run, not a live race.

    2.1 Canonical run topology#

    The Worker and Grader branches run in parallel during the round. They join only after both are sealed: worker evidence is frozen, and grader criteria are frozen. This preserves blind evaluation and makes post hoc rubric adaptation impossible within the same round.

    3. The Node Atlas: one authority behind the civilization#

    3.1 Why the current node representations should be unified#

    The current architecture has at least four related structures:

    • WIP tasks that agents claim;
    • a deliverable skeleton tree with ownership, trust, grading, gaps, and lineage;
    • a resource map with claim/recapture and yields;
    • progressive-disclosure stage contents.

    All are useful, but if they are independently generated or updated they can disagree. A task can close without correct task credit; a deliverable node can be marked complete while no useful resource claim appears; disclosure can advance from a score that did not grade the same node evidence; or the Council's resource design can be canonicalized away.

    The refinement is to store one authoritative NodeAtlas and expose derived projections:

    NodeAtlas (source of truth)
   ├── WipProjection             claimable atomic work and leases
   ├── DeliverableProjection     integration and publication structure
   ├── ResourceProjection        capture, ownership, yields, recapture
   ├── DisclosureProjection      visible payload by group and stage
   ├── GradingProjection         proof contracts and node score history
   └── LineageProjection         agents → artifacts → nodes → final output

    Existing tables and APIs can remain during migration, but writes should converge through a single atlas transaction.

    3.2 Receiver-why decomposition#

    The Council begins from the final receiver, not from a list of sections to write.

    Receiver and situation
        ↓ why is a deliverable needed?
Receiver outcome / decision
        ↓ what must be true for that outcome?
Acceptance obligations
        ↓ what prevents each obligation?
Limitations and uncertainty
        ↓ what capabilities remove each limitation?
Knowledge / evidence / model / tool / experiment nodes
        ↓ what is the smallest independently verifiable unit?
Atomic leaf nodes assigned to mortal agents

    Execution runs in the opposite direction: atomic leaves are researched, built, tested, connected, and integrated until the final deliverable root becomes possible.

    Design hypothesis H-A. Limitation-oriented atomic leaves will give short-lived agents clearer success conditions than document-section tasks, while the hidden receiver rationale will prevent early agents from merely imitating the final answer. The hypothesis is falsified if node completion and downstream reuse do not improve relative to section-based WIP at matched cost.

    3.4 Node atomicity rules#

    A Council-produced leaf is valid only when all of the following hold:

    1. It contains one dominant limitation or question, not a disguised list.
    2. A single mortal agent can normally produce a useful attempt within one TTL.
    3. It has an observable proof contract and at least one acceptable artifact type.
    4. Dependencies are explicit and acyclic.
    5. Failure can be recorded as a useful dead end or uncertainty result.
    6. The node can be graded without inferring the agent's private reasoning.
    7. It maps to at least one receiver obligation, directly or through ancestors.
    8. It does not reveal more of the final task than allowed by its stage.
    9. If independent replication is useful, the replication mode and required count are explicit.
    10. If a tool or simulation could reduce repeated effort, that opportunity is represented explicitly.

    A useful compiler heuristic is:

    estimated_agent_effort(node) <= 0.6 × median_agent_TTL

    The remaining TTL is reserved for retrieval, tool use, verification, staging, and the death commit.

    3.5 Public skeleton, hidden payload#

    Every group should see that a fixed map exists, but not necessarily what every future node means.

    Always visible in the map skeleton:

    • node ID;
    • kind;
    • layer/depth;
    • prerequisite edges;
    • current ownership and contest state;
    • reward class and congestion level;
    • payload hash;
    • reveal condition.

    Revealed only by stage or accepted amendment:

    • limitation statement;
    • receiver-why excerpt;
    • proof details;
    • suggested source domains;
    • hidden tests;
    • final deliverable relationship.

    This provides strategic topology without leaking the root answer. Payload hashes prove that the Council did not rewrite future requirements after seeing group behavior.

    4.3 Council generation sequence#

    1. Preserve operator input. Store raw objective and artifact hashes.
    2. Model the receiver. Identify who will use the deliverable, what decision it supports, why it is needed, and which failures are unacceptable.
    3. Generate competing interpretations. Where the receiver intent is ambiguous, create branches rather than silently choosing one.
    4. Decompose limitations. Build obligations → limitations → capabilities → atomic leaves.
    5. Identify proof types. Decide which leaves need sources, calculations, tests, simulations, tools, or integration.
    6. Build disclosure stages. Reveal enough to make each stage meaningful without exposing the final root too early.
    7. Design the resource economy. Attach bounded, instrumental rewards to nodes.
    8. Generate the grader field. Define evaluation frontier nodes and calibration artifacts without seeing future worker outputs.
    9. Compile and lint. Run deterministic validation.
    10. Selectively regenerate failures. Rerun only the Council role responsible for invalid structures.
    11. Seal. Store exact JSON, schema version, hashes, and consistency report.

    4.4 Deterministic StartingFieldCompiler#

    The Council's synthesis output should be treated like source code, not trusted configuration prose.

    The compiler must verify:

    • exact raw-objective preservation;
    • group counts and models fit the execution envelope;
    • all role assignments resolve to available backend IDs;
    • the node graph is acyclic and roots are reachable from leaves;
    • mandatory stages have at least one feasible frontier;
    • every node has a valid proof, capture, and reveal policy;
    • atomic leaves fit TTL bounds;
    • hidden payload hashes are present;
    • reward totals cannot exceed configured per-round or cumulative caps;
    • no worker-visible context contains forbidden future-stage fields;
    • grader hidden tests are committed before round 0;
    • all KG relation IDs and aliases compile;
    • the final output contract is explicit;
    • the worker and grader fields agree on node and rubric schema versions.

    Compiler result:

    sealed interface StartingFieldCompileResult {
    data class Valid(
        val workerField: StartingField,
        val graderField: StartingField,

    Forbidden behavior: materially changing group count, topology, model family, stage count, or node lineage after sealing without producing a new field version and degradation report.

    4.5 Cheap-model Council mode#

    Large all-at-once JSON synthesis is a predictable failure point for cheap models. Use a staged compiler interface:

    • one schema per Council role;
    • bounded arrays and explicit maximum node counts;
    • deterministic IDs generated by the runtime, not the model;
    • relation and enum values supplied as constrained choices;
    • partial parse and field-level retry;
    • compiler-generated repair prompts containing only invalid fields;
    • no full Council rerun when one resource node is malformed;
    • structural checks before semantic LLM review.

    A stronger model may improve receiver decomposition and synthesis, but reliable field generation should not depend on it.

    5.2 Disclosure progresses from foundation to receiver deliverable#

    A robust default is four conceptual layers, though the Council may choose more.

    Stage Worker-visible question Typical nodes What remains hidden
    0 — Foundations What basic facts, parameters, mechanisms, and uncertainties must be resolved? Knowledge, evidence, simple model, tool primitives. Final product identity and receiver trade-offs.
    1 — System capability How do these primitives combine into functional subsystems? Simulations, subsystem models, validation, alternatives. Full receiver context and delivery format.
    2 — Receiver constraints Under what real-world conditions must the system work, and whose needs dominate? Trade-offs, safety, cost, accessibility, governance, integration. Final presentation contract or remaining strategic intent.
    3 — Delivery What complete artifact will allow the receiver to act, and why? Integration, decision, final deliverable, verification. Nothing material; root contract is revealed.

    This is why-to-how in Council generation, but how-to-why in worker experience.

    5.3 Stage advancement#

    Advancement should be node-coverage based, not a single opaque total.

    stagePass(group, stage) =
    validVerdict
    AND graderQuorum
    AND all mandatory prerequisite nodes >= nodeThreshold
    AND no unresolved mandatory hard failure
    AND evidenceCoverage >= stageEvidenceThreshold
    AND integrationReadiness >= stageIntegrationThreshold

    If evaluation is invalid:

    INVALID verdict  → freeze stage, no penalty, no leak escalation, open diagnostic
ABSTAINED quorum → request tie-break or carry forward, no resource mutation
VALID failure    → hold stage and issue current-stage limitation feedback
VALID pass       → reveal next payload set and apply earned yields next round

    This directly prevents the historical failure in which unreliable score aggregation affected disclosure and leak multipliers. [S4:546–566]

    5.4 Feedback must not leak hidden stages#

    Each grader rationale is split into:

    • internalRationale: may reference full receiver contract and hidden criteria;
    • workerFeedback: redacted to current-stage limitations, failed evidence, and actionable next steps;
    • futureDisclosureNote: encrypted or sealed until the relevant stage.

    A feedback linter rejects terms, node IDs, or receiver details from unrevealed stages.

    6. Competitive worker and delivery groups#

    6.1 Same landscape, independent trajectories#

    Worker groups receive the same Atlas skeleton and stage rules but retain:

    • separate substrate databases;
    • separate canon, tools, dead ends, and legacy;
    • different group profiles and costs;
    • independent node portfolios;
    • controlled leaks and dispatches;
    • independent candidate deliverables.

    The goal is not to preassign each group a designer-authored worldview. Groups should choose how to overcome the landscape under their economics. Diversity emerges through node scarcity, different accumulated knowledge, outlier amendments, tools, and competition.

    6.3 Congestion and frontier incentives#

    To avoid the historical 100% task overlap:

    • show how many groups have bid on each node;
    • increase reward for uncrowded mandatory nodes;
    • reduce discovery yield for redundant unplanned submissions;
    • preserve validation credit for deliberate INDEPENDENT_K work;
    • award an integration bonus for resolving contradictory independent results;
    • expose a group-level frontier diversity score to the selector.

    A simple congestion multiplier:

    adjustedNodeYield = baseYield × (1 + frontierBonus) / sqrt(1 + unplannedCompetitors)

    Quality grading remains independent of congestion; only the economic yield changes.

    Archivist Consolidation/indexing Round handoff, canonical index, duplicate/dead-end links. Win primary worker legacy from summary volume.
    Educator Knowledge transfer nodes Compressed reusable guidance and onboarding. Replace source evidence with explanation.
    Outlier No ordinary WIP lease Novelty vector proposal and falsifiable test. Receive legacy or a specific hidden target.

    The lifecycle-bound Critic authority may remain the final promotion boundary, as accepted by the current roadmap. The important change is that a content-writing Critic cannot masquerade as independent review. [S2:129–140]

    6.5 Context-limited agent packet#

    Each mortal worker receives only:

    1. stable role charter;
    2. current stage card;
    3. Atlas skeleton with hidden payloads;
    4. one assigned node card, or Outlier mandate;
    5. a small retrieved evidence packet;
    6. relevant predecessor death notes and dead ends;
    7. available tool cards;
    8. a contribution contract;
    9. TTL and budget state.

    The packet should be built by retrieval and hard token limits. Agents should not load the whole KB merely because it exists. Durable memory is valuable precisely because it can be queried rather than copied into every context.

    7. Mortal-agent TTL and useful-death protocol#

    7.1 Mortality is a first-class execution constraint#

    The current lifecycle already gives finite iterations, budgets, grace periods, and Death Notes. [S1:65–103, 251–295] The refinement is to make usefulness a typed state transition rather than a prompt request.

    SPAWNED
  → ORIENTING
  → WORKING
  → COMMIT_REQUIRED
  → CONTRIBUTION_STAGED | NEGATIVE_RESULT_STAGED | NO_CONTRIBUTION
  → DEATH_NOTE_WINDOW
  → TERMINATED

    Suggested TTL checkpoints:

    TTL fraction Runtime action
    0–65% Normal work.
    65% Warn agent and expose remaining budget.
    80% Require selection of commit type and target artifact IDs.
    90% Disable new broad exploration; allow verification, staging, and note writing.
    95% Read-only Death Note grace except final commit transaction.
    100% Terminate and finalize accounting.

    7.3 Fallback policy#

    Historical runs generated “tool abstention rationale,” synthetic plan updates, or fallback scores when models failed to use tools or return structured shapes. [S1:1156–1186] The refined policy is:

    • fallback artifacts enter a dedicated DEGRADED_EXECUTION channel;
    • they do not close a node;
    • they do not earn staging or task fitness;
    • they may produce a Dead End if they contain specific reproducible failure information;
    • repeated fallback triggers model-capability or prompt remediation telemetry;
    • the group may respawn a replacement agent if the node remains important and budget allows.

    useful_exit_rate = useful mortal exits / all ordinary mortal exits

    This is a more meaningful mortality metric than “agent completed normally.”

    8. Outlier protocol: novelty without a disguised assignment#

    8.1 Outlier information and mandate#

    An Outlier sees:

    • the current revealed map;
    • aggregate node congestion;
    • recent dead ends;
    • known assumptions and contradictions;
    • prohibited duplication examples;
    • no ordinary node assignment;
    • no legacy protocol;
    • no hidden receiver contract.

    Its only instruction is to introduce a useful, testable novelty vector.

    • cross-domain analogy;
    • new tool or simulation layer;
    • adversarial attack;
    • simplification that removes unnecessary work;
    • new evidence source class;
    • missing integration dependency.

    8.2 Shadow nodes#

    Accepted proposals become SHADOW nodes for one or more rounds. They are visible as group discoveries but do not mutate the sealed base map until evaluated.

    PROPOSED → DUPLICATE_CHECKED → SHADOW_NODE → TESTED
         → ACCEPTED_AMENDMENT | REJECTED | DEFERRED

    Grader groups score:

    • novelty relative to revealed and hidden Council map;
    • receiver relevance;
    • testability;
    • plausibility;
    • expected impact;
    • cost;
    • downstream adoption.

    If a proposal independently anticipates a hidden future Council node, it should receive “anticipatory discovery” credit without revealing the future payload immediately.

    8.3 Guardrails against random novelty#

    An Outlier proposal receives no reward when it is:

    • unconnected to any visible limitation;
    • impossible to test;
    • merely a wording variation;
    • already present in the revealed map or canon;
    • materially more expensive than its expected benefit without justification;
    • dependent on hidden information the Outlier should not possess.

    Outlier fitness should be delayed until a later agent or group tests, adopts, or rejects the vector with evidence.

    9.1 Why the tool loop must become central#

    9.4 Delayed tool fitness#

    Creation alone earns limited credit. Full fitness arrives only after downstream reuse.

    toolFitness =
    validationPasses
  + uniqueLaterAgentsUsingTool
  + successfulRuns
  + nodeScoreDeltaAttributedToResults
  + avoidedRepeatedCost
  - failures
  - maintenanceCost

    A simulation tool is especially valuable when it reduces uncertainty across several later nodes.

    9.5 Cheap-model-compatible tool building#

    Cheap models often struggle with arbitrary multi-file code, tool-call continuation, and strict schemas. The architecture can compensate with:

    • generated project skeletons;
    • constrained DSLs for formulas, rules, and simulations;
    • one file and one function per atomic tool node;
    • compiler and test output fed back in short repair loops;
    • runtime-generated JSON schemas and enum values;
    • deterministic wrappers around model-written logic;
    • property-test templates;
    • forbidding promotion without actual sandbox execution;
    • assigning stronger models only to failed critical tool nodes, not the whole run.

    For many domains, a small declarative simulator is safer than unrestricted code generation.

    10. Competitive grader civilizations#

    10.1 The grader branch has two competitions#

    Grader groups compete in:

    1. Requirement discovery: who creates the widest, deepest, most robust, creative, and executable evaluation framework before worker outputs are known?
    2. Judgment quality: whose judgments are calibrated, discriminative, reproducible, and predictive of final receiver success?

    The current architecture already creates isolated grader databases, criteria agents, authored sheets, tests, and RoundJudges. S2 reports current deterministic acceptance for the grader civilization and isolated scoring process. [S2:105–118] The refinement is to make grader quality an explicit node landscape rather than letting deterministic seed artifacts dominate fitness.

    10.2 Grader Atlas#

    The Grader Genesis Council produces a separate GraderAtlas with evaluation frontier nodes such as:

    • receiver-obligation coverage;
    • failure-chain depth;
    • evidence authenticity;
    • uncertainty handling;
    • adversarial robustness;
    • reproducibility;
    • integration coherence;
    • tool-result validity;
    • cost/benefit realism;
    • accessibility and stakeholder effects;
    • hidden-test design;
    • rubric calibration;
    • false-positive reduction;
    • novel failure-mode discovery.

    Grader agents claim these nodes exactly as workers claim limitation nodes.

    10.5 Grader competition score#

    A grader group's own score should be a multi-objective vector:

    Dimension Example measurement
    Breadth Fraction of receiver obligations and worker-node proof classes covered.
    Depth Number and quality of causal failure chains, thresholds, and edge cases.
    Robustness Adversarial cases, uncertainty treatment, and resistance to superficial compliance.
    Creativity Valid unique failure modes or tests not present in other grader groups.
    Executability Share of requirements backed by deterministic or sandboxed tests.
    Calibration Agreement with anchors, deterministic tests, or human/external calibration subset.
    Discrimination Ability to distinguish intentionally varied artifacts without arbitrary noise.
    Predictive validity Whether high-scored nodes later integrate successfully into final delivery.
    Parsimony Coverage and fault detection per criterion/token/cost.
    Actionability Whether feedback causes measurable node improvement next round.

    Do not reward number of requirements alone. Rubric bloat is a failure mode.

    10.6 Exact-cardinality score bundles#

    The historical run's zero/nonzero/zero aggregation pattern must remain a permanent regression test even if current code has been repaired. [S4:177–255]

    10.7 MetaJudge authority#

    The MetaJudge should remain bounded and deterministic where possible:

    1. validate bundle identity and cardinality;
    2. run deterministic test results;
    3. normalize scores using the sealed policy;
    4. calculate disagreement and confidence;
    5. detect single-grader critical failures;
    6. request a tie-break only for contested material dimensions;
    7. persist exact aggregation trace;
    8. emit VALID, INVALID, or ABSTAINED verdict status.

    A single novel critical failure should not automatically zero a group. It should create a contested requirement requiring evidence or a tie-break.

    10.8 Same-family grader caveat#

    When all worker and grader agents use the same model family, the system may still test orchestration, but grader independence is weak. The verdict should include:

    This prevents a single-family test run from being misrepresented as three independent evaluators.

    11.2 Executable round sequence#

    1. Snapshot the Atlas. Resolve prior amendments, ownership, yields, and stage visibility.
    2. Build group views. Generate per-group WorkerView hashes.
    3. Select node portfolios. Apply replication and congestion rules.
    4. Spawn mortal worker agents. Each receives a node lease or Outlier mandate.
    5. Spawn grader criteria agents in parallel. They work on the Grader Atlas.
    6. Run and monitor TTL. Enforce contribution checkpoints and typed events.
    7. Freeze grader criteria. Validate, Critic-review, and seal criteria before worker evidence reveal.
    8. Freeze worker groups. Terminate remaining agents after commit/death-note grace.
    9. Run worker Critic authority. Promote/reject staging and close only valid node contributions.
    10. Package NodeEvidencePackets. Include all accepted artifacts, claims, tool runs, tests, and negative results.
    11. Seal anonymized group snapshots. Worker group identity is hidden from graders.
    12. Run blind node and group judging. Each grader produces exact bundles.
    13. Validate MetaJudge quorum. Invalid rounds cannot mutate disclosure, capture, leak pressure, or fitness.
    14. Grade grader groups. Use deterministic anchors, requirement quality, and judgment quality.
    15. Resolve capture/recapture. Decide ownership node by node.
    16. Apply bounded yields for the next round. Never retroactively alter current-round judging.
    17. Decide disclosure. Use mandatory node coverage and valid verdict status.
    18. Emit redacted feedback. Current-stage limitation gaps only.
    19. Compute causal fitness and legacy. Worker, control, grader, and summary roles remain in separate pools.
    20. Archive round. Require no live ordinary or grader agents and complete cost/event reconciliation.
    21. Repeat or publish. If root delivery nodes are unlocked and the round ceiling permits, generate final candidates; otherwise proceed.

    11.3 Pseudocode#

    suspend fun executeRound(ctx: RunContext, round: Int): RoundOutcome {
    val atlasSnapshot = atlasService.sealRoundSnapshot(ctx.runId, round)
    val workerViews = disclosureService.buildWorkerViews(atlasSnapshot)
    val portfolios = portfolioService.allocate(workerViews, ctx.executionEnvelope)

    val workerJob = workerRunner.runGroups(workerViews, portfolios)
    val graderCriteriaJob = graderRunner.buildCriteria(round, atlasSnapshot.graderView)

    val sealedCriteria = graderCriteriaJob.awaitAndSeal()
    val workerResult = workerJob.awaitOrTerminateWithDeathCommits()
    val promoted = criticAuthority.review(workerResult.staging)
    val evidence = evidencePackager.seal(promoted, atlasSnapshot.hash)

    val bundles = graderRunner.blindJudge(sealedCriteria, evidence)
    val verdict = metaJudge.validateAndAggregate(bundles)

    if (!verdict.isValidWithQuorum) {
        return roundService.freezeWithoutMutation(round, verdict)
    }

    val captures = captureService.resolve(verdict.nodeGrades)
    val yields = yieldService.scheduleForNextRound(captures)
    val disclosure = disclosureService.decide(verdict, captures)
    val fitness = fitnessService.computeFromLineage(promoted, verdict, captures)

    return roundService.archiveAndComplete(
        round, verdict, captures, yields, disclosure, fitness
    )
}

    12.3 Capture states#

    LOCKED → REVEALED → OPEN
                   ├── NO_EVIDENCE
                   ├── PROVISIONAL_CAPTURE
                   ├── CAPTURED
                   ├── CONTESTED

    • best grade above threshold receives ownership;
    • near ties may be contested or share validation credit;
    • later materially better evidence may recapture;
    • ownership never changes grader weights or access to hidden criteria;
    • all capture decisions are replayable from bundles and policy.

    12.4 Instrumental reward types#

    Reward Intended use Guardrail
    SPAWN_CREDITS One additional mortal agent on a future frontier. Per-group and per-round cap.
    TOOL_COMPUTE_CREDITS More sandbox executions or simulation runs. Only for tool/simulation-related capture.
    SOURCE_ACCESS_CREDITS More approved fetches or evidence processing. Still subject to allowlist and audit.
    RETRIEVAL_BUDGET Larger top-k or richer context pack, not unlimited context. Hard context ceiling remains.
    DISCLOSURE_TOKEN Early reveal of one optional adjacent node. Cannot reveal mandatory future root or hidden tests.
    DISPATCH_CREDITS Send one formal cross-group challenge or request. Delayed and trust-scored.
    MODEL_TIER_COUPON Upgrade one critical role call. Optional; disabled in iso-model benchmarks.
    LEGACY_SLOT Preserve a causally successful protocol. Requires successor A/B evidence.

    Rewards apply in the next round. This avoids a race in which early same-round capture changes resources before all groups are judged.

    12.5 Anti-rich-get-richer constraints#

    • diminishing marginal yield for repeated ownership by one group;
    • maximum fraction of total active yields controlled by one group;
    • frontier bonus for uncaptured mandatory nodes;
    • validation credit for second groups that independently reproduce a result;
    • recapture remains possible;
    • invalid/abstained evaluation freezes all yields;
    • control-plane or grader-plane nodes cannot grant worker-canon authority;
    • optional underdog access to one non-sensitive leak or tool card when capture concentration exceeds a threshold.

    12.6 Resource usefulness telemetry#

    Every yield should carry a causal record:

    node captured → reward granted → reward spent → downstream artifact → score delta

    If a reward is consistently unused or has no downstream value, the Incentive Designer's policy should lose fitness in later Council evaluations.

    Pool Eligible roles What counts
    Worker Researcher, Builder, Planner, Connector, Educator, Outlier Accepted nodes, reuse, validation, novelty adoption, efficiency.

    13.4 Legacy retention#

    A protocol is conditioned on:

    (role archetype, node kind, subtask class, model capability profile,
 prompt version, tool set, disclosure stage, group profile)

    It is retained only when a successor A/B comparison shows positive lift. Outliers receive no legacy. Control and summary legacy never enters ordinary worker prompts.

    13.5 Dead-end quality#

    A useful Dead End must record:

    • attempted node and method;
    • inputs, tool versions, and sources;
    • observed failure;
    • why the result falsifies or weakens an approach;
    • confidence and unresolved ambiguity;
    • conditions under which retry might be justified;
    • successor alternatives.

    A blank or generic failure map is not promoted.

    15.1 What the supplied evidence says#

    The architecture supports OpenRouter and Qwen Cloud; a text-only compatibility path removes the tool registry and asks for plain-text output.     These are configuration observations, not proof that every cheap model behaves identically. They do identify five model-sensitive bottlenecks:

    1. strict structured-output compliance;
    2. native tool-call continuation;
    3. executable code/simulation construction;

    5. evaluator independence and calibration.

    15.3 What can be achieved with cheap, single-family models#

    A cheap single-family configuration is suitable for:

    • engine plumbing and lifecycle tests;
    • Atlas generation on bounded objectives using staged compiler repair;
    • atomic research and document fragments;
    • simple claim extraction;
    • basic rubric generation;
    • small tools from templates or DSLs;
    • multi-round substrate accumulation;
    • capture, disclosure, and resource mechanics;
    • deterministic test and scoring-path validation.

    It is not strong evidence that competition created independent cognition. When workers and graders share a model family, correlated blind spots can survive all groups.

    15.4 Outcomes likely to require a different setup#

    The following claims or results may require selective model diversity or stronger calls:

    • reliable discovery of genuinely orthogonal approaches rather than prompt-styled variants;
    • robust adversarial grading independent of worker biases;
    • sophisticated executable simulation tools with low repair overhead;
    • correct decomposition of ambiguous receiver motives into deep limitation trees;
    • high-quality final integration across many contested nodes;
    • defensible claims of society superiority over a strong single-agent baseline.

    “Require” should be treated empirically. The architecture should expose triggers rather than hard-code prestige models.

    15.6 Real same-family single-agent differentiation#

    Prompt specialization is useful, but it is not enough to demonstrate that two agents instantiate meaningfully different cognitive policies. EvoMolior can create genuine differentiation while keeping one model family—and, for the cleanest experiment, one exact base checkpoint—by varying learned parameters, hidden-state interventions, decoder policies, expert routing, or inherited adapter lineages.

    Recommended minimum. Treat learned soft prompts or prefixes as the smallest credible model-level change. Treat a role- or lineage-specific LoRA/QLoRA adapter on one shared open-weight base as the preferred practical change. Temperature, random seeds, context shards, and personas may supplement this, but they should not be reported as independent model cognition.

    The expensive part is not necessarily serving the differentiated agents. Modern serving systems can select LoRA adapters per request with relatively low switching overhead; the expensive parts are producing good training data, training and validating candidate adaptations, multi-sample search, and maintaining enough held-out evaluation to prevent reward hacking. Official Qwen tooling supports full tuning, LoRA, QLoRA, DoRA, and several preference/RL methods, while vLLM supports per-request LoRA serving and dynamic adapter loading. These capabilities make a shared-base adapter population technically realistic even when separate full checkpoints would be impractical.

    15.6.3H — Auxiliary learned modules that differentiate the effective agent

    These do not necessarily change the base language model, but they change the agent's learned decision boundary and can be combined with any phenotype above.

    • Role-specific verifier or reward model: selects evidence, code, plans, or grader requirements differently.
    • Tool/action policy head: chooses when and which tool to call before the language decoder writes arguments.
    • Retrieval encoder/reranker: gives agents different learned access patterns over the same substrate.
    • Planner/value model: predicts node value, expected information gain, or failure probability.
    • Uncertainty/calibration head: changes abstention and escalation behavior.
    • Safety or constitutional classifier: gates actions independently of the role prompt.
    • Simulation surrogate: gives a Builder or Researcher a learned world-model component.

    For scientific reporting, call this effective-agent differentiation, not base-model differentiation, and ablate it separately.

    15.6.4 Recommended phenotype stack for EvoMolior#

    The best balance of real differentiation, serving cost, lineage, and rollback is:

    one exact open-weight base checkpoint
    + one compiled adapter per agent
        = role adapter
        + group-culture / lineage delta
        + optional node-class delta
        + bounded per-agent micro-mutation
    + optional learned soft prefix
    + immutable inference policy
    + optional verifier / steering intervention
    + exact phenotype and training-data hashes

    This avoids training a complete model—or even a complete adapter—from scratch for every disposable agent. A small number of reusable components produce many unique phenotypes. Where the serving backend accepts only one LoRA per request, the components are merged and validated into one CompiledAdapterRef before spawn.

    Best first implementation. Self-host one small open-weight checkpoint from the same family used in cheap testing; train a small set of QLoRA role adapters; serve them through a per-request adapter-capable gateway; add a reproducible decoder profile per role; and compare this against the identical checkpoint with prompt-only roles. Only after the uplift is real should group-lineage mutation and crossover be enabled.

    A role adapter alone makes all Researchers similar. To give each mortal agent a genuine individual phenotype without an individual full training job, compile identity from several layers:

    LayerScopeExamplesInheritance rule

    Group adapterCompeting civilizationEvidence-first, simulation-first, risk-first, minimalist cultureUpdated only from that group's accepted lineage.

    15.6.7 Lifecycle and TTL semantics#

    1. Before birth: the selector chooses a phenotype candidate compatible with role, group, node, cost, and experimental arm.
    2. Compile: the phenotype compiler resolves one base checkpoint, one compiled adapter, optional soft state, decoder, verifier, and intervention bundle; it hashes the exact composition.
    3. Capability floor: deterministic smoke tests reject malformed or degraded mutations before they consume a node lease.
    4. Birth: the phenotype is immutable for that agent's entire TTL. The agent cannot update its own adapter, extend its life, or alter its evaluator.
    5. Work and death: observable tool/actions, accepted commit, dead end, and costs are attached to the phenotype hash.
    6. Round barrier: only after sealed grading and causal attribution may a trainer, merger, or mutation engine produce candidate descendants.
    7. Future birth: descendants become eligible only after held-out quality, retention, calibration, and diversity gates.

    This preserves the core product principle: the individual dies; learned lineage persists only through a reviewed substrate artifact.

        clone | bounded mutation | adapter merge | distillation | retraining
  → base-compatibility and safety checks
  → held-out node suite + capability-retention suite
  → behavioral-distance / novelty measurement
  → cost and serving-overhead measurement
  → ACCEPT, QUARANTINE, or REJECT phenotype artifact
  → accepted phenotype becomes eligible next round

    Three inheritance modes should be explicit:

    • Baldwinian: select better adapter IDs, decoder policies, and hyperparameters, but do not alter weights during the run. This is the safest first evolutionary mode.
    • Lamarckian: train or update an adapter from successful observable trajectories and let descendants inherit the learned delta.
    • Crossover/memetic: merge two validated adapter lineages and optionally combine them with a Legacy Protocol. This is the strongest EvoMolior-specific mechanism but should come last.

    15.6.11 Outlier and grader isolation rules#

    • Outliers: may receive larger mutation distance, unusual target modules, soft-prefix perturbations, or a novelty-oriented adapter. They still must pass a capability floor. They receive no ordinary legacy text; their model lineage is a separately labeled novelty lineage.
    • Worker groups: may evolve group adapters only from their own accepted private substrate. Cross-group adapter transfer is a formal leak/dispatch event with provenance, not an invisible copy.
    • Graders: use a separate base or, at minimum, a separate immutable adapter registry and training corpus. A grader phenotype must not descend from worker phenotypes or train online on the same worker outputs it scores.
    • Within-run evaluation freeze: grader adapters and verifier weights are frozen before worker submissions are revealed. Improvements become eligible only in a later round using prior-round anonymized failure telemetry and an independent holdout.
    • MetaJudge: remains deterministic for aggregation. A model may analyze contested rationales but cannot rewrite score bundles or adapter fitness.

    15.6.12 Preventing co-adaptation, monoculture, and reward hacking#

    1. Never train a worker adapter from one scalar LLM-judge score. Require exact tests, accepted/rejected evidence, downstream reuse, or calibrated labels.
    2. Keep train, adapter-selection validation, and final sealed test sets disjoint by task family and source lineage.
    3. Run a general-capability retention suite before accepting any mutation or merge.
    4. Measure error correlation, not only average score. Two high-scoring phenotypes with identical failures do not create useful diversity.
    5. Use Pareto or niche selection over quality, novelty, calibration, cost, and robustness instead of one fitness scalar.
    6. Cap lineage dominance and retain a known-good base/adapter fallback.
    7. Version every base, adapter, merge recipe, dataset, training configuration, and evaluation result by cryptographic hash.
    8. Make rollback atomic. A phenotype that fails post-deployment checks is quarantined without rewriting prior manifests.
    9. Do not let an agent choose or modify its own evaluator, mutation rate, or descendant eligibility.
    10. Keep benchmark arms immutable; evolutionary learning must be predeclared and costed.

    15.6.16 Model-bound limitations that remain even after adaptation#

    • A shared base still carries shared pretraining blind spots. Adapters reduce correlation; they do not guarantee independence.
    • Small cheap bases may learn role style, schemas, or tool habits more easily than deep new reasoning capabilities.
    • Adapters trained from overlapping synthetic data can collapse into nearly identical policies despite different IDs.
    • Per-agent random perturbation is usually harmful unless bounded, screened, and selected against a stable capability floor.
    • Weak or corrupted grader feedback will become more dangerous once it can alter future model weights. Exact bundles, causal fitness, and calibration are prerequisites—not optional hardening.
    • Dynamic LoRA support does not imply arbitrary adapter stacking. Compile or use a validated fusion backend.
    • Tool-call reliability remains a joint property of base model, adapter, prompt, decoder, schema, and runtime continuation protocol.
    • Activation steering, masks, routing changes, and model editing are checkpoint-specific and can have off-target effects.
    • Full training or online RL during every round is likely too slow and expensive for early EvoMolior testing. Use small bases and barrier-batched adapter updates first.
    • Independent high-stakes grading may still require a distinct family, external evaluator, deterministic tests, or human calibration. Same-family grader adapters improve specialization but do not prove independence.

    15.7 Three recommended deployment modes#

    Mode A — Cheap single-family engineering mode#

    • same cheap family across roles;
    • deterministic compiler, validators, scoring, capture, and publication checks;
    • small atomic nodes;
    • constrained tool DSLs;
    • label evaluation independence LOW_SINGLE_FAMILY;
    • purpose: improve runtime correctness and mechanics cheaply.

    Mode B — Cost-efficient mixed production mode#

    • cheap workers and grader researchers;
    • one stronger CouncilSynthesis call if compilation repeatedly fails;
    • one distinct-family or stronger RoundJudge per grader group for final stages;
    • stronger final integrator only after deterministic assembly;
    • model upgrades are selective and logged.

    Mode C — Research-valid comparison mode#

    • worker model family held constant across single-agent and society arms;
    • identical sources, Atlas, tools, output contract, and cost cap;
    • graders use a different family and a human/external calibrated subset;
    • multiple seeds;
    • evaluation independence and provider costs reported.

    18.3 Definition of society improvement#

    The full society should not be considered improved merely because it produces more artifacts. Predeclare one of these success forms:

    • higher receiver-grade quality at the same provider/tool cost;
    • non-inferior final quality at lower cost or lower failure rate;
    • materially greater accepted node coverage, contradiction resolution, or novel failure discovery at a justified cost;
    • reusable tools/simulations that reduce later-round cost or improve validation;
    • greater resilience to agent death and injected failures while preserving output quality.

    The current roadmap reports small matched gains on FRAMES and LitQA2 but research-synthesis ties at materially higher cost and therefore does not claim broad superiority. [S2:142–155] This architecture should preserve that claim discipline.

  │     ├── INTEGRATION: braking and control
  │     ├── INTEGRATION: thermal and safety
  │     └── INTEGRATION: human factors and accessibility

Atomic leaves include:
  - rolling resistance and grade-force model
  - braking-distance parameter ranges
  - candidate material strength/mass/cost evidence
  - energy-density and duty-cycle evidence
  - thermal load model
  - tire friction uncertainty
  - occupant geometry constraints
  - manufacturing-process capability evidence

    Workers execute leaf-to-root.

    19.3 Stage 0 worker view#

    Workers do not receive “design a car.” They see a system limitation field such as:

    A human-scale mobile system must convert stored energy to controlled motion, support expected loads, stop safely under uncertain surface conditions, and remain within bounded mass and cost. Resolve the revealed foundational uncertainties.

    Example revealed nodes:

    Node Atomic question Proof Reward
    K-PHYS-01 What forces dominate motion at low/medium road speeds across plausible mass and grade ranges? Equation model, parameter sources, sensitivity. Retrieval/source credits.
    K-BRAKE-02 What braking distance ranges follow from friction, speed, reaction, and load uncertainty? Calculated envelope and assumptions. Validation credits.
    K-MAT-03 Which material families offer feasible strength/mass/cost trade-offs? Evidence table with uncertainty. Context retrieval budget.
    T-SIM-01 Can a reusable dynamics simulator evaluate force, acceleration, energy, and stopping scenarios? Executable typed tool, tests, sandbox runs. Tool-compute credits.
    V-SIM-02 Does the simulator reproduce hand-calculated anchors and edge cases? Independent validation report. Capture bonus and next-stage optional reveal.

    19.4 Round 0 behavior#

    • Group A Researcher claims K-PHYS-01.
    • Group A Builder claims T-SIM-01.
    • Group B Researcher independently claims K-BRAKE-02.
    • Group B Builder competes on T-SIM-01 or chooses a material trade-off tool.
    • Outliers receive no node. One proposes that the map lacks repairability under distributed maintenance, with a falsifiable modularity/cost test.
    • Grader groups independently create requirements for unit consistency, parameter provenance, uncertainty, edge cases, and tool reproducibility before seeing outputs.

    At check-in:

    • each node evidence packet is graded;
    • the better simulator captures T-SIM-01;
    • an independent validation group earns validation credit;
    • the repairability Outlier proposal becomes a shadow node if grader groups find it relevant and testable;
    • the next stage reveals subsystem relationships only if mandatory foundations pass.

    19.5 Stage 1: system capabilities#

    The map now reveals that motion, energy, braking, structure, and thermal behavior must coexist in one wheeled transport platform. The promoted dynamics simulator is available to later agents.

    Agents use it to compare:

    • mass/material alternatives;
    • energy and range scenarios;
    • braking envelopes;
    • grade performance;
    • sensitivity to uncertain friction and load.

    The tool's full fitness is earned only when later nodes cite its executed results.

    19.6 Stage 2: receiver constraints#

    The receiver context is progressively revealed: household use, urban/rural duty cycle, affordability, accessibility, repair network, safety, and manufacturing constraints.

    Groups now resolve trade-offs rather than merely maximizing performance. Graders add requirements around lifecycle cost, maintenance, accessibility, misuse, and unsupported assumptions.

    19.7 Stage 3: delivery#

    The root contract is revealed. Each group assembles its own complete candidate using its captured nodes, tools, and evidence lineage. The final grader round evaluates both the deliverable and the integrity of its ancestry.

    A winning deliverable must show:

    • every required section traces to accepted Atlas nodes;
    • simulator outputs use promoted tool versions and input hashes;
    • receiver trade-offs are explicit;
    • unresolved uncertainty is not hidden;
    • Outlier-originated accepted nodes are either integrated or explicitly rejected with evidence;
    • no unsupported claim appears merely because the final writer is fluent.

    This example illustrates the intended emergence: agents begin by overcoming small limitations, not by imitating a known “car design” answer.

    22. Final architecture judgment#

    The existing high-level architecture should remain intact. Its strongest idea is not a generic multi-agent swarm but a competitive generational process in which bounded agents die and durable institutional state survives.

    The missing center is a coherent limitation landscape. By making the Council-produced Node Atlas authoritative, EvoMolior can align:

    • what agents know;
    • what agents work on;
    • what agents must leave before death;
    • what graders require;
    • what is captured;
    • what resources are earned;
    • what is disclosed next;
    • what tools compound;
    • what fitness preserves;
    • and what the final receiver actually needs.

    The architecture can be developed cheaply with one model family because strict schemas, atomic contexts, deterministic compilers, executable tests, and replayable scoring carry much of the reliability burden. However, a single family should be regarded as a low-cost engineering environment. Truly independent novelty, adversarial grading, difficult simulation construction, and strong claims of improvement over single-agent reasoning will usually need a different evaluation setup and may benefit from selective stronger or heterogeneous models.

    The central implementation principle is:

    Do not add more agents until every current agent has a gradeable limitation, a bounded view, a useful-death contract, and a causal path into the receiver's final outcome—or is an Outlier whose explicit job is to add a new path.
