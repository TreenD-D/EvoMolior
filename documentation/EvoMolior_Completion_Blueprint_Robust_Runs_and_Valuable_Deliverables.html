    EvoMolior Completion Blueprint#

    Robust runs, flexible deliverables, and strict acceptance closure#

    Evidence cut: 24 July 2026
    Status: implementation blueprint derived from the v21 strict-run report, its runtime log, the maintained progressive-disclosure plans, and the earlier EvoMolior architecture action plan.
    Architectural invariant: retain the existing product loop:

    input
  → Genesis Council
  → competitive worker/delivery groups
    + parallel competitive grader groups
  → sealed end-round check-in and evaluation
  → capture, resource, disclosure, repair, and lineage update
  → next round
  → final publication or explicit non-accepted recovery publication

    The project no longer needs another architectural reset. It needs a reliability-and-deliverable completion layer that makes the existing civilization linearizable, repair-capable, and useful to its receiver under both success and failure.

    Executive decision#

    The latest strict run materially changes the remaining work. Earlier failures were dominated by startup schema transport, Council compilation, test executability, incomplete grader authority, and missing runtime paths. In v21, the system instead demonstrated that it can:

    • package and admit an immutable distribution;
    • complete Genesis Council and compile eight executable sealed tests;
    • run two worker societies for all six rounds;
    • run three grader civilizations in every round;
    • complete exact broad-score submissions without a final grader outage;
    • preserve all round summaries;
    • reject mandatory-failing candidates rather than inventing a winner;
    • produce an explicit non-acceptance recovery archive.

    The run still failed because two low-level control contracts and one product-output contract remain incomplete:

    1. Lifecycle state is not linearizable. A stale budget-monitor write can overwrite a newer frozen exit state, causing repeated immutable-exit conflicts.
    2. Tool repair is not a first-class typed learning loop. The system can detect many contract defects, but it cannot safely communicate enough semantic information for later agents to repair a hidden-test failure.
    3. Recovery publication is administratively correct but receiver-useless when no scoring candidate exists. The system preserves summaries but does not compile them into a decision package.

    These are now the critical path. The next implementation should be organized around six closure programs:

    Program Outcome Priority
    Lifecycle linearizability Exactly one durable exit identity and a deterministic quiescence boundary P0
    Tool contract transport Agents edit implementations, not immutable runtime contracts P0
    Typed semantic repair Safe, bounded, cross-generation feedback that enables repair without leaking private fixtures P0
    Deliverable compiler Receiver-oriented semantic packages rendered to multiple formats P0
    Recovery publication Useful provisional deliverables without creating winner or acceptance authority P0
    Deterministic acceptance simulator Reproduce the entire six-round success and failure paths before another expensive provider run P0

    A fresh strict provider run should occur only after all six programs pass a clean, immutable, deterministic gate cycle. The v21 run must remain immutable and must never be resumed or reclassified.

    1.3 What should not be reopened#

    The following boundaries have sufficient current evidence to remain regression-protected rather than redesigned:

    • the macro Council → competitive workers/graders → sealed check-in loop;
    • the receiver-oriented Node Atlas and redacted WorkerView architecture;
    • exact grader cardinality and no-zero-fill policy;
    • criteria freeze before worker evidence reveal;
    • fail-closed capture, disclosure, and publication;

    • immutable distribution admission;

    • final archive quiescence requirement;
    • Outlier separation from ordinary work and Legacy;

    The completion plan extends these mechanisms; it does not weaken them.

    2. Target product contract: every run returns a useful, honest outcome#

    The product should expose three terminal outcome classes. A binary COMPLETED versus FAILED view is too coarse for a research civilization that may create substantial useful evidence before missing one strict acceptance condition.

    @Serializable
enum class RunOutcomeClass {
    ACCEPTED_DECISION_PACKAGE,
    PROVISIONAL_DECISION_PACKAGE,
    STARTUP_DIAGNOSTIC_PACKAGE,
}

    2.1 Accepted decision package#

    Created only when all normal authority gates pass:

    • accepted scoring candidate and winner/source authority;
    • all mandatory sealed tests pass;
    • required node coverage and final lineage are complete;
    • active reservations are zero;
    • registered exits reconcile exactly;
    • all non-daemon agents are quiescent;
    • publication state reaches ARCHIVED;
    • manifest verification succeeds.

    This package carries normal final-reference and acceptance authority.

    2.2 Provisional decision package#

    Created after meaningful worker/grader rounds when strict acceptance fails. It must:

    • state clearly that no accepted winner exists;
    • preserve all mandatory failures and missing authority;
    • compile public committed evidence from every eligible group;
    • compare alternatives without silently ranking them as accepted;
    • identify receiver-safe conclusions, contested conclusions, and blocked conclusions;
    • identify the exact missing evidence or tool authority needed to upgrade the result;
    • never create a normal winner, final reference, accepted metric packet, or acceptance archive.

    This is the principal missing v21 product feature.

    2.3 Startup diagnostic package#

    Created when the run fails before worker activation. It should include:

    • failing phase and typed error codes;
    • candidate field/test hashes where safe;
    • exact declared/compiled/preflight cardinality;
    • admission/distribution identity;
    • operator-actionable remediation;
    • no private fixture content;
    • no receiver decision claims.

    2.4 Meaning of a “proper deliverable”#

    A deliverable is proper when it is receiver-oriented rather than a dump of agent prose. It must have:

    1. an explicit audience and decision/use;
    2. required semantic components;
    3. evidence and uncertainty lineage;
    4. a declared authority class for every component;
    5. deterministic tables and metrics where possible;
    6. at least one human-readable format;
    7. at least one machine-readable format;
    8. a manifest binding every emitted file;
    9. stable rendering independent of the final LLM’s formatting preferences;
    10. a usable failure form that does not imply acceptance.

    New cross-cutting layers#

    4. Workstream A — Make lifecycle state linearizable#

    4.1 Design rule#

    LiveAgentEntry must no longer be a value repeatedly replaced in a concurrent map by unrelated code paths. The map should contain one stable per-agent runtime cell. All state transitions occur through that cell’s atomic reducer.

    class AgentRuntimeCell(
    initial: AgentRuntimeState,
) {
    private val mutex = Mutex()
    private var state: AgentRuntimeState = initial

    suspend fun <T> mutate(
        operation: String,
        transform: (AgentRuntimeState) -> MutationResult<T>,
    ): T = mutex.withLock {
        val result = transform(state)
        validateTransition(state, result.next)
        state = result.next
        result.value
    }

    suspend fun snapshot(): AgentRuntimeState =
        mutex.withLock { state }
}

    ConcurrentHashMap<AgentId, AgentRuntimeCell> remains suitable for cell registration and lookup. It should not be used as the lifecycle-state mutation mechanism.

    4.2 Monotonic state model#

    @Serializable
enum class AgentRuntimePhase {
    CREATED,
    RUNNING,
    TERMINATION_REQUESTED,
    EXIT_AUTHORITY_FROZEN,
    EXECUTION_FINISHED,
    ACCOUNTING_FINALIZED,
    QUIESCENT,
}

@Serializable
data class AgentRuntimeState(
    val agentId: String,
    val runId: String,
    val groupId: String,
    val role: Role,
    val phase: AgentRuntimePhase,
    val killRequested: Boolean,
    val executionFinished: Boolean,
    val exitAuthority: AgentExitRecord?,
    val deathCallbackEmitted: Boolean,
    val budgetSnapshot: AgentBudgetSnapshot?,
    val ledgerRegistered: Boolean,
    val ttlCheckpoints: Set<Int>,
    val costSettlement: CostSettlementState,
    val version: Long,
)

    Required invariants#

    • phase may move only forward.
    • killRequested may move only false → true.
    • executionFinished may move only false → true.
    • exitAuthority is write-once and byte-immutable.
    • exitedAt is generated once, when exit authority is frozen.
    • budget, ledger, and TTL telemetry cannot change lifecycle fields.
    • death callback is emitted exactly once.
    • lease/WIP cleanup uses the frozen wasKilled and exit reason.
    • a durable exit does not imply quiescence until the runner actually finishes.
    • cost settlement must complete before QUIESCENT.

    4.3 Mutation APIs#

    No caller should receive a mutable or copyable whole state object. Expose intent-specific methods:

    suspend fun registerLedger(snapshot: AgentBudgetSnapshot)
suspend fun publishBudget(snapshot: AgentBudgetSnapshot)
suspend fun addTtlCheckpoint(percent: Int)
suspend fun requestTermination(reason: TerminationReason): AgentExitRecord
suspend fun markExecutionFinished(completion: RunnerCompletion)
suspend fun markCostSettled(settlementId: String)
suspend fun markDeathCallbackEmitted()
suspend fun markQuiescent()

    Each implementation derives the next state from the current state inside the cell lock. A previously captured AgentRuntimeState must never be written back.

    4.4 Exit ordering#

    The required order is:

    1. Atomically freeze AgentExitRecord in runtime cell.
2. Persist the exact record idempotently.
3. Finalize Atlas lease and WIP from the frozen record.
4. Request runner cancellation or graceful termination.
5. Await actual runner completion.
6. Mark executionFinished using the same frozen exit authority.
7. Complete non-cancellable cost settlement.
8. Emit the once-only death callback.
9. Reconcile durable registration-to-exit counts.
10. Mark the cell QUIESCENT and remove only after archival snapshot.

    Late completion must read the frozen exit authority. It must never create a new exit timestamp or termination identity.

    4.5 Persistence behavior#

    The substrate’s immutable-exit check is correct and must remain strict. Add an idempotent repository result:

    sealed interface PersistExitResult {
    data object Inserted : PersistExitResult
    data object AlreadyPresentExact : PersistExitResult
    data class Conflict(
        val existingHash: String,
        val attemptedHash: String,
    ) : PersistExitResult
}

    AlreadyPresentExact is normal during recovery or duplicate delivery. Conflict is a fatal runtime invariant failure, not a retryable warning.

    The current repeated five-second retry loop should be removed. A conflict cannot heal by retrying the same mismatched identity.

    4.6 Required tests#

    Deterministic barrier regression#

    LifecycleExitLinearizabilityTest.ttl kill concurrent with budget publication preserves one exit

    1. Start an in-process worker with a registered ledger.
    2. Pause the worker at a controlled cancellation barrier.
    3. Trigger TTL termination and persist the frozen exit.
    4. Concurrently publish budget, ledger, and TTL-checkpoint updates.
    5. Release cancellation.
    6. Assert exactly one durable exit record and hash.
    7. Assert no immutable conflict and no deferred retry.
    8. Assert exactly one death callback.
    9. Assert lease/WIP cleanup uses the frozen wasKilled.
    10. Assert active reservation count is zero.
    11. Assert the runner is finished before quiescence.

    Property/stress regression#

    Randomly interleave:

    • budget publication;
    • checkpoint publication;
    • graceful completion;
    • TTL kill;
    • operator abort;
    • cost settlement;
    • death callback;
    • monitor scans.

    For at least thousands of deterministic schedules, assert the monotonic invariants and one exit identity.

    Restart regression#

    Freeze and persist exit authority, terminate the process before runner completion, reload the run, and ensure recovery reuses the exact persisted exit while waiting for/cleaning orphan execution state.

    The v21 failure distribution shows that too much model capacity is being spent reproducing runtime-owned schemas and identifiers. This is the same class of failure previously solved for grader methodologies with short handles.

    5.1 Tool opportunity binding catalog#

    5.4 Canonical numeric serialization#

    Do not ask the model to reason about JSON lexical number canonicalization in every candidate. Supply one runtime serializer for test values and local outputs.

    • parse model-authored typed values;
    • encode through the same canonical serializer used by promotion;
    • reject non-finite numbers before encoding;
    • preserve INTEGER versus NUMBER distinctions from the sealed schema;
    • display corrected public canonicalization errors immediately while the agent is alive.

    The model still authors expected semantics; the runtime owns the byte representation.

    5.5 Contract transport acceptance#

    A candidate transport path passes only if:

    • the model cannot change the opportunity or schemas;
    • all exact IDs are resolved from a capability-bound handle;
    • source and tests are content-hashed;
    • the compiled submission independently reproduces the sealed contract hash;
    • the model-facing prompt contains no private promotion fixture;
    • the existing production validator receives the same domain object as before.

    5.6 Tests#

    • ToolOpportunityBindingCatalogTest: stale/foreign/duplicate handles reject.
    • ToolCandidateWireCompilerTest: schemas and opportunity IDs come only from runtime authority.
    • ToolWorkspaceTamperTest: edits under contract/ fail hash verification.
    • ToolCanonicalNumberCompilerTest: NUMBER and INTEGER values serialize consistently.
    • ToolTransportRegressionV21Test: literal v21 schema-mismatch and missing-schema drafts compile correctly or fail before model review with a single actionable wire error.

    6.4 Safe disclosure policy#

    A disclosed diagnostic may contain:

    • the enum code;
    • a generic remediation statement from a checked-in dictionary;
    • the affected public output field handle, if that field is already visible;
    • the relevant public unit/dimension metadata;
    • source class and round.

    It must not contain:

    • private input values;
    • private expected or actual outputs;
    • private numeric differences;
    • hidden test names when those names are private;
    • paths, URLs, stack traces, or exception text;
    • raw Critic prose;
    • another group’s implementation;
    • model-private reasoning.

    6.5 Typed Critic semantic output#

    The tool Critic should return a typed review:

    @Serializable
data class ToolSemanticReview(
    val verdict: ToolSemanticVerdict,
    val publicFindings: List<PublicToolFinding>,
    val safeRepairCodes: Set<ToolRepairCode>,
    val privateRationaleCommitment: String,
)

    The deterministic boundary validates that every safe code is compatible with the public contract. Arbitrary prose is stored only as private review material and is never pattern-matched into worker context.

    6.6 Quantity and unit semantics#

    The power-to-energy failure should also be preventable or classifiable through typed unit metadata.

    Council compilation should reject contradictions such as:

    For Python tools that cannot be fully dimension-checked statically, the reference semantics and public tests should still carry typed quantity expectations so the Critic can emit a safe category.

    6.7 Prompt correction#

    Remove any statement that workers will receive private expected and actual outputs. Replace it with:

    Your public tests prove local consistency only. Private promotion authority is separate.
Private fixtures and exact private outputs are never disclosed.
You may receive:
- exact public contract/schema diagnostics;
- public canonical-number diagnostics;
- public reference semantics and quantity metadata;
- bounded safe semantic repair codes from a previous generation.
Treat these codes as hypotheses to test, not as hidden fixture values.

    6.8 Repair lifecycle and causal credit#

    @Serializable
data class ToolRepairAttemptRecord(
    val attemptId: String,
    val opportunityId: String,
    val candidateHash: String,
    val authorAgentId: String,

    A diagnostic is useful only if a later candidate consumes it and changes the relevant behavior. Fitness should reward:

    • a diagnostic that enabled a later promotion;
    • a repair candidate that promoted;
    • a repair candidate that converted a hidden failure into a different, narrower failure;
    • a structured dead end that prevents repeated identical attempts.

    It should not reward the mere production of diagnostics.

    6.9 Scheduling and diversity#

    When a mandatory tool node remains open with repair diagnostics:

    • keep it high in the group’s next-round portfolio;
    • assign a worker with exact repair context;
    • cap lineage attempts to prevent infinite repetition;
    • require the two competing groups to receive distinct sealed ApproachVectors when explicit replication would otherwise produce correlated retries.

    Example strategy vectors:

    Group A: dimensional-analysis-first; derive units and reference calculations before code.
Group B: property-test-first; build invariants and boundary cases before implementation.

    The approaches are sealed before the candidate is produced and become part of experiment lineage.

    6.10 End-to-end repair regression#

    PowerToEnergyRepairAcceptanceTest should prove:

    1. First candidate passes public shape checks but fails private promotion.
    2. Private values remain inaccessible.
    3. Critic safely emits POWER_TO_ENERGY_UNIT_CONVERSION.
    4. The diagnostic is visible only in a later permitted generation.
    5. A new agent consumes the code.
    6. The corrected implementation divides the watt-hour total by 1000 for kWh output.
    7. Existing private fixture passes.
    8. The tool promotes.
    9. A different later mortal agent executes it on the sealed reuse node.
    10. A simulation record enters a later evidence packet and affects grade/capture.

    • content hash;
    • whether an LLM transformed the content or it was deterministically assembled.

    7.4 Deterministic versus model-authored content#

    Use deterministic assembly for:

    • test results;
    • node coverage;
    • option comparison rows;
    • numerical metrics;
    • evidence tables;
    • risk registers with typed source rows;
    • assumptions and uncertainties;
    • accepted/provisional badges;
    • missing-authority lists;
    • manifests and provenance.

    Use the final LLM only for:

    • receiver-language synthesis;
    • connecting accepted components;
    • explaining trade-offs already present in evidence;
    • producing concise narrative transitions.

    The LLM must not invent values for missing tool results or silently upgrade provisional evidence.

    8.3 Recovery comparison rules#

    The comparison assembler may state:

    • where groups agree;
    • where they disagree;

    • that a mandatory-failing recommendation is accepted;

    9. Workstream F — Integrate repair and deliverables into the round loop#

    The round loop should have an explicit closure order. Repair feedback and deliverable snapshots should not be incidental side effects.

    ROUND START
  1. Freeze matched worker/Grader Atlas pair.
  2. Apply due yields and permitted repair diagnostics.
  3. Compile group portfolios and agent runtime cells.
  4. Freeze grader frontier and methodology work.

PARALLEL EXECUTION
  5. Spawn mortal worker agents with immutable node authority.
  6. Spawn grader criteria agents without worker evidence.
  7. Accept public same-lifetime tool preflight feedback.
  8. Terminate/complete agents through linearizable runtime cells.

SEALED ROUND END
  9. Run Critic promotion and typed semantic review.
 10. Seal evidence packets and tool/simulation records.
 11. Freeze grader criteria.
 12. Reveal exact worker evidence to graders.
 13. Persist exact grader bundles and deterministic sealed-test outcomes.
 14. Resolve grades, capture, yields, disclosure, and Outlier authority.
 15. Publish safe ToolRepairDiagnostic records for future permitted rounds.
 16. Compile interim deliverable snapshots.
 17. Archive the round phase ledger.

NEXT ROUND OR TERMINAL
 18. Activate next-round Atlas amendments and diagnostics.
 19. Continue, accepted publication, or provisional recovery publication.

    Same-lifetime versus cross-generation feedback#

    • Public deterministic preflight: may be returned immediately to the living tool author.
    • Public Critic semantic category: normally visible next generation, unless current policy explicitly permits same-round repair before the Critic boundary closes.
    • Private promotion category: visible only in later permitted generations and only as a safe code.
    • Private values: never visible.

    Make this policy explicit in ToolRepairDiagnostic.visibleFromRound; do not rely on incidental timing.

    10.2 Success scenario#

    The scripted scenario must execute the real production sequence:

    1. Council compiles a valid two-stage Atlas, eight executable tests, and one feasible tool path.
    2. Round 0 creates atomic evidence and one first tool candidate.
    3. Candidate fails private authority with a safe unit-conversion diagnostic.
    4. A TTL kill occurs concurrently with a budget update.
    5. Exactly one exit identity persists and the runner reaches quiescence.
    6. Round 1 repair worker consumes the diagnostic and submits a corrected candidate.
    7. Tool passes private promotion and becomes the sole active version for the opportunity.
    8. A different later mortal agent receives the exact validation/use card.
    9. VALIDATION_TEST and later AGENT_USE remain distinct.
    10. Successful execution produces a simulation record.
    11. The record enters a later evidence packet and affects grade/capture.
    12. Mandatory nodes pass and disclosure advances.
    13. Final package references accepted nodes, tool execution, uncertainty, and receiver decision.
    14. All costs settle and all agents become quiescent.
    15. Manifest v4 verifies and publication ends ARCHIVED.

    • recovery manifest verifies;
    • private fixtures remain absent.

    12. Model and backend implications#

    12.1 What the latest run says about the current model setup#

    The all-Luna, medium-effort configuration can now sustain:

    • strict Council generation;
    • six-round worker execution;
    • three grader civilizations;
    • exact broad-score cardinality;
    • long provider-backed orchestration.

    The remaining semantic tool failure does not by itself prove that the model family is inadequate. The system still asks the model to perform avoidable transport work and provides insufficient safe feedback after a hidden failure.

    12.2 Correct order of intervention#

    1. Remove immutable-contract transcription through handles and generated workspaces.
    2. Add typed semantic diagnostics and unit metadata.
    3. Add strategy differentiation between replicated groups.
    4. Measure promotion and repair success.
    5. Only then decide whether a stronger or fine-tuned Builder/Critic is necessary.

    Fine-tuning before stabilizing the protocol risks training the model to reproduce temporary wire formats and current failure modes.

    12.3 When selective stronger models become justified#

    Route selectively when the post-protocol evidence shows one of these:

    • tool candidates pass transport but repeatedly fail semantic private tests;
    • complex simulations exceed the cheap model’s implementation reliability;
    • Council repair frequently exhausts attempts on coherent typed contracts;
    • grader requirements remain shallow or highly correlated;
    • final synthesis cannot preserve accepted lineage.

    The high-volume leaf work can remain on cheaper models; stronger calls should concentrate on Council Synthesis, Builder repair, semantic Critic review, and final receiver synthesis.

    12.4 Same-family correlation#

    When two groups are assigned the same mandatory tool node using the same model family, prompt-only differences may not create sufficient independence. Use explicit sealed strategy vectors now, and later role/group adapters when the fine-tuning infrastructure is ready.

    Do not describe multiple same-family graders as fully independent. Preserve the existing low-independence label until an external family or calibrated evaluator is introduced.

    18. Final definition of done#

    18.1 Runtime correctness#

    • exactly one durable exit identity for every registered ordinary agent;
    • zero lifecycle identity conflicts and zero exit-finalization retries;
    • all non-daemon executions finished before normal or recovery archive closure;
    • all cost reservations settled;
    • exact grader cardinality and replay error zero;
    • no private fixture leakage.

    18.2 Tool compounding#

    • at least one Council-sealed tool/simulator candidate passes private promotion;
    • only one active version exists per opportunity;
    • a different later mortal agent executes it under exact node authority;
    • validation and AGENT_USE are distinct when the Atlas requires both;
    • the execution creates a simulation/tool-result record;
    • that record enters later evidence and changes grade, capture, integration, or receiver decision lineage;
    • repair diagnostics and consumption lineage are persisted.

    18.3 Deliverable value#

    • the Council seals a receiver-oriented DeliverableBlueprint;
    • every sealed round produces recoverable interim snapshots;
    • accepted completion emits all required package components;
    • non-accepted completion emits a provisional decision package, not only an administrative notice;
    • every claim/component is accepted, provisional, or withheld explicitly;
    • machine-readable evidence and human-readable output agree;
    • renderer failure cannot erase semantic package authority.

    18.4 Archive and metrics#

    • exit marker 0 for accepted completion;
    • summary and pipeline summary COMPLETED;
    • winner/source/writer authority present;
    • results.zip and pipeline-results.zip verify;
    • manifest v4 verifies every entry and outcome-specific invariant;
    • all 21 Section 18.2 observations exist with valid availability/evidence;
